# Inteligencia Artificial aplicada al negocio

## Curso autodidacta — material de aprendizaje

**Audiencia:** personas y equipos que buscan mejorar tareas reales con IA.

**Nivel:** inicial, sin programación requerida.

**Duración sugerida:** 4 horas de lecciones y actividades, más el desafío final.

**Resultado:** diseñar un piloto de IA acotado, medible y supervisado para un proceso de negocio.

---

# Clase abierta gratuita

## Encuentra una tarea donde la IA pueda ayudar de verdad

**Duración:** 20 minutos.

**Objetivo:** terminar con una oportunidad concreta escrita en una tarjeta de piloto, no con una lista de herramientas.

### Lección

Cuando una organización comienza a explorar IA, una pregunta habitual es “¿qué herramienta deberíamos comprar?”. Para diseñar una solución que realmente ayude, conviene empezar con otra: **¿qué tarea de una persona queremos mejorar y qué resultado debería cambiar?**

La inteligencia artificial no arregla por sí sola un proceso que nadie entiende. Primero observa el trabajo actual. Identifica qué lo inicia, quién participa, qué información se consulta, qué decisión se toma y quién recibe el resultado. Después busca una tarea en la que leer, clasificar, resumir, comparar o redactar consuma tiempo de manera repetida.

Una IA generativa puede producir una propuesta útil, pero esa propuesta no debe confundirse con un hecho verificado. Por eso conviene asignarle tareas delimitadas: por ejemplo, sugerir una categoría para una solicitud o preparar un resumen para revisión. La persona responsable confirma el resultado cuando un error puede afectar a un cliente, un pago, una decisión sensible o el cumplimiento de una regla.

### Caso de práctica (ficticio)

Un equipo recibe solicitudes internas por correo. Las personas deben leer cada mensaje, decidir a qué área corresponde y resumir qué necesita quien lo envió. En este ejercicio imaginario, se propone probar una IA que sugiera una categoría y redacte un resumen breve. El equipo mantiene la decisión final y corrige las sugerencias antes de derivar la solicitud.

El ejemplo **no representa un caso ni un resultado real de ArkoData**. Sirve para practicar cómo definir el límite entre una sugerencia automática y una decisión humana.

### Cuatro preguntas para evaluar una oportunidad

1. **¿La tarea está clara?** Puedes describir su inicio, sus pasos y su resultado.
2. **¿Se repite?** Si ocurre con frecuencia, una pequeña mejora puede beneficiar muchas veces al equipo.
3. **¿Hay información suficiente?** La solución necesita datos de entrada y ejemplos con los que comprobar su respuesta.
4. **¿Qué pasa si se equivoca?** Define excepciones, impacto y el punto en que una persona debe revisar o detener el flujo.

No son una fórmula para decidir automáticamente. Son preguntas para descubrir qué falta antes de experimentar.

### Actividad: tarjeta de oportunidad

Escribe respuestas breves:

| Pregunta | Tu respuesta |
|---|---|
| ¿Quién realiza la tarea y quién recibe el resultado? | |
| ¿Qué activa el trabajo? | |
| ¿Qué pasos se repiten? | |
| ¿Qué información usa la persona? | |
| ¿Qué parte podría preparar o sugerir la IA? | |
| ¿Qué decisión debe permanecer bajo supervisión humana? | |
| ¿Qué observarías para saber si el piloto ayuda? | |

**Entrega:** una tarjeta clara que otra persona del equipo pueda entender. No incluyas nombres de clientes, datos personales, documentos privados ni información confidencial.

### Comprueba lo aprendido

**1. ¿Qué conviene definir primero?**

- A. El modelo más avanzado.
- B. La tarea, sus usuarios y el resultado que se desea mejorar. **(Correcta)**
- C. La cantidad de automatizaciones posibles.

**2. La IA propone una categoría para una solicitud delicada. ¿Qué diseño es más responsable?**

- A. Derivar automáticamente todos los casos sin revisar.
- B. Mostrar la sugerencia, validar la categoría y derivar excepciones a una persona. **(Correcta)**
- C. Ocultar la sugerencia al equipo.

**3. ¿Qué evidencia ayuda a evaluar un piloto?**

- A. Una observación definida antes de probarlo, como el tiempo de revisión o la proporción de correcciones. **(Correcta)**
- B. Que la solución use una herramienta nueva.
- C. El número de mensajes enviados a la IA.

**Respuestas:** 1-B, 2-B, 3-A. **Criterio sugerido:** 2 de 3 correctas para completar la muestra.

# Curso pagado

## Módulo 1 — Comprender el trabajo y elegir el caso

### Lección 1.1: Una IA generativa no es una fuente de verdad

Los sistemas generativos producen una respuesta a partir de patrones aprendidos y del contexto que reciben. Pueden redactar, resumir, transformar y clasificar contenido con fluidez. La calidad de esa respuesta depende de la tarea, los ejemplos, el contexto y la forma en que se revise.

Una respuesta bien escrita puede contener un dato equivocado, una omisión o una conclusión que no se desprende de la información proporcionada. Esto no significa que la tecnología no sirva; significa que el proceso debe especificar qué puede proponer, cómo se valida y qué ocurre cuando no hay suficiente evidencia.

Separa tres actividades:

- **Preparar:** resumir, ordenar o proponer una categoría.
- **Comprobar:** contrastar el resultado contra fuentes y reglas autorizadas.
- **Decidir:** aceptar, corregir, rechazar o escalar el caso.

Para tareas de bajo impacto, una persona puede revisar muestras y excepciones. Para tareas con consecuencias mayores, define una validación más estricta antes de usar el resultado. La autonomía se asigna según el riesgo y la evidencia disponible; no viene incluida automáticamente con el modelo.

**Ejercicio:** escribe una instrucción de una tarea de tu equipo y marca con tres colores qué parte puede preparar una IA, qué debe comprobarse y quién decide.

### Lección 1.2: Del dolor operativo a un problema acotado

Una oportunidad es más útil cuando tiene un dueño, un límite y un resultado observable. “Mejorar atención” es demasiado amplio. “Ayudar al equipo a resumir solicitudes entrantes para que las clasifique una persona” delimita una tarea y conserva la decisión final.

Usa este enunciado:

> Para **[usuario o equipo]**, queremos ayudar con **[tarea específica]** usando **[información permitida]**. El sistema entregará **[resultado esperado]**. Una persona revisará **[casos o decisiones]**. Evaluaremos el piloto observando **[medida]**.

Antes de elegir una herramienta, busca ejemplos representativos del trabajo y documenta las excepciones. Si el equipo no coincide en cómo debería resolverse un caso, primero acuerda la regla. No es razonable esperar que el modelo resuelva por sí solo una política de negocio que todavía no existe.

**Ejercicio:** reescribe un objetivo amplio de tu organización usando el formato anterior. Pide a un compañero que identifique quién usa el resultado y qué acción tomaría después.

## Módulo 2 — Diseñar instrucciones útiles y resultados verificables

### Lección 2.1: Una instrucción de trabajo precisa

Una petición vaga deja demasiadas decisiones implícitas. Para reducir ambigüedad, especifica el propósito, la tarea, el contexto autorizado, los límites y el formato de salida. Revisa la instrucción con ejemplos reales antes de conectarla a un proceso.

Plantilla para practicar:

```text
Propósito: [para qué se usará el resultado]
Tarea: [acción delimitada]
Contexto: [información autorizada]
Límites: [qué no debe inferir ni hacer]
Salida: [campos, extensión y lenguaje]
Revisión: [quién valida y cuándo escalar]
```

Ejemplo didáctico:

```text
Tarea: propone una categoría para el mensaje recibido.
Categorías permitidas: acceso, pago, consulta general, otra.
Usa solamente el texto proporcionado. No inventes datos.
Si no hay evidencia suficiente, responde "revisión humana".
Entrega categoría y una frase de motivo.
La categoría es una sugerencia; una persona confirma la derivación.
```

La instrucción no reemplaza una regla programable. Si una condición es exacta y estable —por ejemplo, derivar todos los casos con un campo vacío— es preferible expresarla como regla verificable.

**Ejercicio:** crea una instrucción para la tarea que definiste en el módulo 1. Incluye una condición de “no sé” o de escalamiento.

### Lección 2.2: Ejemplos, salidas y límites

Los ejemplos muestran qué se considera una buena respuesta y qué hacer ante situaciones distintas. Incluye un caso común, uno ambiguo y uno que deba escalarse. No uses datos personales reales en ejemplos de aprendizaje; reemplázalos por datos ficticios o anonimizados.

Define la salida antes de conectar el modelo. Por ejemplo: `categoría`, `resumen` y `requiere_revision`. Luego comprueba que cada campo exista, tenga el tipo esperado y respete el catálogo permitido. Una salida que parece estructurada todavía debe validarse en el sistema que la recibe.

**Ejercicio:** prepara tres ejemplos de entrada con la salida esperada. Incluye uno donde el modelo deba abstenerse y explica el motivo.

## Módulo 3 — Evaluar y proteger el piloto

### Lección 3.1: Evalúa con casos, no con impresiones

Antes de probar una solución, conserva una muestra de casos y define cómo evaluarás la respuesta. Las medidas dependen de la tarea: exactitud de categoría, campos que requieren corrección, casos correctamente escalados o tiempo de revisión. No combines varias medidas en una sola cifra sin explicar qué representa.

Revisa también los errores por tipo. Un promedio aceptable puede esconder una categoría que falla sistemáticamente. Comprueba los casos ambiguos, los cambios de formato y las entradas incompletas. Cuando cambies la instrucción o el modelo, vuelve a correr las mismas pruebas para observar si mejoró o empeoró.

**Ejercicio:** construye una tabla de diez casos ficticios o debidamente autorizados. Registra respuesta esperada, respuesta obtenida, error y acción humana. Propón una condición para pausar el piloto.

### Lección 3.2: Datos, privacidad y revisión humana

Entrega al modelo solo la información necesaria para la tarea y aprobada para ese uso. Revisa las políticas de tu organización, la configuración del proveedor y las obligaciones aplicables antes de introducir datos personales, sensibles o confidenciales. Quitar el nombre de un archivo no siempre anonimiza su contenido.

Define permisos, retención, responsables y controles de acceso. Asegura que el sistema no convierta una recomendación en una decisión final sin la revisión que requiere el contexto. Registra quién valida las excepciones y cómo corregir un resultado que ya entró al proceso.

El marco NIST para IA generativa propone gestionar riesgos durante el ciclo de vida del sistema; sus recomendaciones son una guía de gestión, no una garantía de que una solución particular sea segura.

**Ejercicio:** clasifica la información de tu caso en “permitida”, “requiere autorización” o “no usar”. Describe qué debe hacer el flujo cuando recibe información no permitida.

## Módulo 4 — Diseñar un piloto y comunicar resultados

### Lección 4.1: Plan de prueba con personas

Un piloto útil responde una pregunta concreta. Define alcance, responsable, participantes, fuentes autorizadas, medida inicial, criterios de revisión, excepciones y condición de cierre. Avisa a las personas involucradas qué hace el sistema y qué no hace.

Compara el nuevo flujo con el proceso actual en condiciones parecidas. Registra el tiempo total, el esfuerzo de revisión y los tipos de error relevantes. Si el tiempo baja pero la tasa de corrección sube, el resultado no es automáticamente una mejora. Decide el balance antes de mirar los resultados.

**Ejercicio:** completa un plan de una página con una semana de preparación y una muestra acotada. Define quién puede detener la prueba y cómo se informará un problema.

### Lección 4.2: Decidir qué hacer después

Al terminar, resume lo observado con límites claros: tamaño de la muestra, tareas evaluadas, excepciones y cambios realizados. Distingue resultados medidos de expectativas. Decide si corresponde ajustar, ampliar con nuevos controles o detener el piloto.

No extrapoles automáticamente una prueba pequeña a toda la organización. La ampliación cambia usuarios, datos, carga y consecuencias. Repite la evaluación cuando cambie cualquiera de esos factores de manera importante.

**Desafío final:** presenta una oportunidad, una instrucción de trabajo, tres casos de prueba, una medida inicial, un esquema de revisión humana y una recomendación sustentada en lo observado.

## Evaluación final autocorregible

**1. ¿Qué describe mejor la salida de una IA generativa en un proceso?**

- A. Un dato verificado automáticamente.
- B. Una propuesta que debe validarse según la tarea y el riesgo. **(Correcta)**
- C. Una decisión de negocio definitiva.

**2. ¿Qué se debe hacer antes de escoger la herramienta?**

- A. Definir tarea, usuarios, información y resultado esperado. **(Correcta)**
- B. Conectar todas las fuentes de datos.
- C. Automatizar el proceso completo.

**3. Si falta evidencia para clasificar una entrada, la instrucción debería:**

- A. Adivinar la categoría más frecuente.
- B. Escalar o indicar que no hay información suficiente. **(Correcta)**
- C. Inventar un campo para completar la salida.

**4. ¿Para qué sirven casos de prueba representativos?**

- A. Para medir el comportamiento, encontrar fallas y comparar cambios. **(Correcta)**
- B. Para demostrar que el modelo nunca se equivoca.
- C. Para reemplazar las reglas del negocio.

**5. ¿Qué evidencia apoya una decisión de ampliar el piloto?**

- A. Una mejora observada en medidas definidas y revisadas junto con sus errores y límites. **(Correcta)**
- B. Que el modelo responda con seguridad.
- C. Que el piloto haya terminado.

**Criterio de aprobación propuesto:** 4 respuestas correctas de 5 y entrega del desafío final. Configurable en el curso.
